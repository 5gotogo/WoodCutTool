# WoodCutTool content-column roadmap, 2026–2027

Updated: 2026-07-31

## Objective

Build a durable woodworking knowledge system in which every search-shaped question leads to a useful action: diagnose a problem, verify a method, calculate a result, download a reproducible example, or open CutList. Page count is a capacity metric, not the goal. New pages must add a distinct intent, project input, diagnostic test, dataset, or decision workflow.

## Editorial architecture

Each major subject should become a connected eleven-layer cluster:

1. A topic hub maps the subject, pillar, supporting decisions, and practical actions.
2. A glossary page defines the term.
3. A Learn pillar explains the complete method.
4. Troubleshooting pages isolate failure-shaped queries, diagnostic tests, and stop conditions.
5. A template provides a project-specific starting point.
6. An example publishes complete inputs, a finished reference state, and downloadable data.
7. A component model calculates one reusable assembly from measured variables and exposes the resulting parts.
8. A checklist verifies the release gate before irreversible work.
9. A worksheet records the project-specific evidence, owner, date, and revision.
10. A Project Playbook connects six project-specific phases, consequential decisions, local progress, and the relevant evidence surfaces into one end-to-end execution path.
11. A calculator, dataset, or CutList link lets the reader calculate, export, or continue the work.
12. One-Sheet Projects provides a visual, constraint-first discovery path into qualifying examples and templates without creating duplicate project-detail URLs.

Blog posts should introduce timely or narrow questions and feed readers into these durable layers. They should not duplicate a Learn guide or troubleshooting page merely to increase volume.

## Sustainable publishing cadence

Use a four-week production cycle rather than publishing every surface at once:

- Week 1: inventory queries, collision-check slugs, and define the action or evidence for each page.
- Week 2: create one generator-backed batch and verify representative output early.
- Week 3: generate, add contextual internal links, refresh sitemap, and run site plus SEO audits.
- Week 4: inspect mobile and desktop pages, measure index weight, review duplication, and record the next backlog.

A normal cycle should ship one coherent batch: 10–20 high-detail pages, 20–40 structured pages with strong unique inputs, 5–12 independently calculated Component models, or one downloadable research dataset plus its report. Larger batches are acceptable when the data shape enforces uniqueness and validation.

## Quality gates for every batch

- Source lives in a generator or data module; generated HTML is not the authoritative edit.
- Slugs and titles are unique across the target surface.
- Every page answers one distinct user intent in its opening section.
- Local links resolve to real pages and lead to an appropriate next action.
- Project claims distinguish nominal size, usable size, kerf, trim, rotation, completion, and purchasing assumptions.
- Research downloads contain the rows needed to reproduce reported totals.
- Checklist pages define one release point, seven observable checks, explicit pass criteria, a stop condition, and a downloadable record.
- Safety, structural, hardware, electrical, plumbing, and code limits are stated where relevant.
- Representative desktop and 390px pages have no overflow, unreadable tables, or contrast failures.
- Every Learn topic hub names one pillar, links its complete guide set, defines evidence and a stop condition, exposes four practical actions, and passes the 650-word/five-inbound-source gate.
- Every Component model has independent formulas, a static default result, strict rejection of zero or negative live dimensions, model/version/source boundaries, CSV and JSON output, a model-specific worked example and release decision, a first-article stop condition, at least four real inbound sources, and a passing cross-page distinctiveness audit.
- Every Project Playbook owns one distinct end-to-end execution intent rather than repackaging a Template or Example; it has six project-specific phases, at least three decision branches with visible downstream consequences, a first-screen action, versioned browser-local progress with a usable storage-failure fallback, CSV and print output, real project-specific safety stop gates, at least 1,250 visible words, at least four independent inbound sources, `Article`, `HowTo`, `FAQPage`, and breadcrumb structured data, one self-canonical without parameterized saved states, and passing 390px and desktop QA.
- One-Sheet Projects must be derived from the versioned benchmark source, include only complete one-sheet results, expose every qualifying example/template/CSV route, provide one master CSV, keep filter states non-canonical, keep saved shortlists browser-local with a storage-failure fallback, and pass dataset-count, 390px, desktop, and local-link checks.
- The required generate, sitemap, site check, SEO audit, and `git diff --check` steps pass.

## Measurement plan

Review performance by cluster every quarter using search-console and first-party analytics data when available. Track indexed URLs, impressions, clicks, query coverage, tool transitions, CutList/app transitions, example and checklist downloads, and pages with no meaningful impressions after six months. Do not delete a low-traffic page automatically: first decide whether it supports a high-value cluster, a real user workflow, or a required evidence trail.

For Project Playbooks, establish a baseline before setting any improvement target. Measure hub-to-playbook opens, first-screen starts, phase completion by stage, browser-local save success versus fallback use, return-and-resume events when privacy-safe first-party analytics can observe them, decision-branch interaction, CSV and print exports, and transitions to the linked Template, Example, Component, Worksheet, Checklist, Troubleshooting, calculator, and CutList surfaces. Record only route, playbook, phase, event type, and storage outcome; never send entered dimensions, notes, checklist state, CSV rows, or raw `localStorage` content. Review abandonment by phase and broken-link or storage-fallback rates quarterly, but do not claim a retention, completion, or conversion lift until a comparable observed baseline exists.

For content maintenance, prioritize pages with one of these signals:

1. High impressions and weak click-through: improve title and direct answer.
2. Traffic with weak tool transition: strengthen the next action and input handoff.
3. Multiple pages ranking for the same intent: consolidate the cluster.
4. A page citing an old product, price, standard, or workflow: verify and refresh it.
5. A generated page without a distinct input, test, or decision: improve or remove it from future generation.
